# Pub launcher installation and verification

The Dart package `failforge` provides the `failforge` command. Launcher `0.2.1`
selects native FailForge `0.2.0`, including offline HTML export, using pinned
archive and package manifest SHA-256 digests for Linux x64 (glibc), macOS arm64
and Windows x64. Native archives provide the Rust executables, Dart adapter and
runtime notices; no Rust installation is needed on the user's machine.

The adapter at `adapters/dart` remains an internal package with
`publish_to: none`. Publishing it alone would not provide the native CLI.

## Install from pub.dev

Use a stable Dart SDK `>=3.13.0 <4.0.0`, or Flutter with a Dart SDK in that range.
On macOS or Linux:

```sh
dart pub global activate failforge 0.2.1
```

Add Pub's executable directory to `PATH` if needed; its default is
`$HOME/.pub-cache/bin`. A custom `PUB_CACHE` changes that directory.

On Windows, remove a previous Pub global entry with
`dart pub global deactivate failforge` if one exists, then use PowerShell:

```powershell
dart install failforge@0.2.1
```

Add the installation bin directory printed by `dart install` to `PATH`.
On every platform, prepare and check the runtime:

```sh
failforge setup
failforge --version
```

Keep the compatible SDK on `PATH` or set `DART_SDK` for adapter preparation and
mutation analysis. The [launcher quickstart](https://github.com/AnuarAbitay/fail-forge/blob/main/packages/failforge/README.md)
covers target preparation, mutation runs, HTML export, cache settings and
uninstallation. Local checkout installation is an additional development route,
shown below; it is separate from hosted package acceptance.

## Local checks

Use a stable Dart SDK `>=3.13.0 <4.0.0`:

```sh
cd packages/failforge
dart pub get --enforce-lockfile
dart format --output=none --set-exit-if-changed .
dart analyze
dart test
dart pub publish --dry-run
```

The dry run validates and lists the package contents without uploading it.
Review that list before publication. The package should contain the launcher,
package metadata, README, CHANGELOG, LICENSE and NOTICE. Runtime downloads,
SDKs, local caches, reports and credentials do not belong in the Pub payload.

Check the `pubspec.yaml` content as part of that review:

- `name: failforge`, the intended package version and an accurate description.
- The supported Dart SDK range and only hosted or SDK dependencies.
- `executables` mapping the `failforge` command to `bin/failforge.dart`.
- Repository, issue tracker and supported platform metadata.
- No `publish_to: none` in the launcher package; retain it in the internal adapter.

From the repository root, exercise activation with a disposable Pub cache if
you need to keep the existing global installation unchanged:

```sh
export PUB_CACHE=/absolute/path/to/disposable-pub-cache
dart pub global activate --source path packages/failforge
"$PUB_CACHE/bin/failforge" setup
"$PUB_CACHE/bin/failforge" --version
```

On Windows, test the standard native CLI installer in a disposable install
directory as well as a disposable Pub cache:

```powershell
$env:PUB_CACHE = 'C:/absolute/path/to/disposable-pub-cache'
$env:DART_DATA_HOME = 'C:/absolute/path/to/disposable-dart-data'
$package = (Resolve-Path 'packages/failforge').Path.Replace('\', '/')
dart install "failforge@{path: '$package'}"
$launcher = Join-Path $env:DART_DATA_HOME 'install/bin/failforge.bat'
& $launcher setup
& $launcher --version
```

Run this example from the repository root. The batch command generated by
`dart install` starts the compiled native launcher. Legacy Pub global/VM
entry points are rejected on Windows before setup or a campaign starts because
the outer Dart VM broker cannot preserve Ctrl+Break cleanup and exit status.
When migrating an existing installation, first remove its stale command with
`dart pub global deactivate failforge`; manage the new installation with
`dart installed` and `dart uninstall failforge`.

Then use a prepared test package to run `doctor`, generate a profile and execute
a small mutation campaign. Check reports, source preservation and cleanup.
Also check Ctrl+C during a campaign, installation paths containing spaces,
repeated invocations, concurrent setup and recovery after interrupted setup.

## Historical launcher verification

The records below cover the prepublication `0.1.0-beta.1` launcher selecting
native `0.1.0` and its follow-up fix snapshot, before the final `0.2.0` pins.
They retain their original source and platform scope; they are not hosted
installation results or CI results for another package revision.

### Local verification, 2026-11-10

On macOS arm64 with Dart 3.13.5:

- All 69 package tests passed, including argument/stdio preservation, Unix
  cancellation, independent SDK/Pub cache contexts and interprocess setup locks.
- Formatting and Dart analysis passed.
- `dart pub publish --dry-run` reported 0 warnings and a 17 KB compressed
  package. It did not upload anything.
- Local activation in a separate Pub cache downloaded the pinned native 0.1.0
  archive from GitHub over HTTPS and prepared its adapter at the final path.
- The installed command passed `--version`, `--help`, `doctor` and profile
  generation. A real Dart campaign produced one `KILLED` mutant, score 100%,
  exit code 0. Target inputs and the runtime's manifested payload stayed intact.
- All three native release archives extracted and passed manifest verification;
  execution through this launcher was checked on macOS arm64 only.

Local receipts and the saved mutation report are under the ignored directory
`artifacts/pub-launcher-20261110/`; `verification.json` records the commands and
source/payload checks. Local path activation may print dependency-resolution
messages from Pub before native stdout.

### Windows verification, 2026-11-11

On Windows 11 Pro for Workstations x64 with Dart 3.13.5, launcher
`0.1.0-beta.1` and native release `0.1.0`:

- The 23 transferred package files matched the source snapshot. Formatting,
  analysis and the test suite passed: 62 tests passed and 7 Unix-specific
  tests were skipped.
- Activation through Pub's generated `failforge.bat`, fresh runtime download,
  adapter preparation, version/help, `doctor` and profile generation passed.
- A real mutation campaign produced one `KILLED` mutant and score 100%, with
  exit code 0. Target inputs and the runtime payload stayed unchanged; temporary
  workspaces were cleaned.
- Ten isolated console cases compared a delayed-cleanup fixture, the Dart
  wrapper, native CLI and the activated Pub batch command. Ctrl+C returned 130
  through both native and Pub entry points. Ctrl+Break returned 143 directly
  from the native CLI, but `0xC000013A` through the Pub launcher. The fixture
  comparison confirmed the wrapper can exit before child cleanup completes.
- A deterministic failed archive-write probe reproduced the unhandled
  `IOSink.done` error on Windows: exit 255, without executing the outer catch
  or finally block.

These pre-fix results established the two defects addressed by the follow-up
verification below. Every console probe's owned Job Object drained, and the
final process audit found no remaining test processes.

Receipts, source hashes, repro scripts and the independently hash-verified
result archive are under `artifacts/pub-launcher-windows-20261111/` (ignored).
Its `verification.json` records that pre-fix result and links the extracted
evidence.

### Fix verification, 2026-11-11

The prepublication fix snapshot passed formatting, analysis and its full test
suite on all three local test hosts with Dart 3.13.5:

| Platform | Passed | Expected skips |
| --- | ---: | ---: |
| macOS arm64 | 85 | 4 Windows console tests |
| Windows x64 | 79 | 10 Unix signal/FIFO/symlink tests |
| Ubuntu 24.04 x64 | 85 | 4 Windows console tests |

Archive writes now await file open, write, flush and close operations. The
original failure probe reaches its catch and finally blocks and returns 125
instead of terminating with an unhandled exception. The regression suite also
checks partial-download removal and successful retry. Unexpected special
manifest, marker and lock entries are rejected before potentially blocking
reads; three POSIX FIFO regressions passed.

Windows now uses `dart install` and its compiled native entry point. A retained
native console callback preserves Ctrl+C/Ctrl+Break while waiting for the Rust
CLI; it does not forward a duplicate cancellation signal. The actual installed
executable and generated batch command returned 130 for Ctrl+C and 143 for
Ctrl+Break, with their native child already stopped. Four isolated console
regressions also verify waiting for a deliberately delayed two-second cleanup.
Legacy VM entry points reject the invocation before creating a runtime cache
and explain how to migrate.

Standard native reinstall, uninstall and restore passed, preserving an unrelated
installation marker and the downloaded runtime cache. The final Windows audit
found no remaining owned processes. Package dry-run passed with 0 warnings;
the compressed package is 19 KB. No upload was performed.

Evidence is retained under `artifacts/pub-fix-windows-break-20261111/` and
`artifacts/pub-html-linux-20261111/`, with the common final package manifest in
`artifacts/pub-fixes-html-20261111/fixed-pub-source-manifest.json`.
The combined result is `artifacts/pub-fixes-html-20261111/verification.json`.

HTML export was separately built from the then-unreleased native source and
exercised in real browsers on Windows and Linux; see
[HTML report verification](html-report.md#platform-verification). At this point,
the prototype still selected native `0.1.0`. The archive and manifest pins were
subsequently updated for launcher `0.2.0`, which selects native `0.2.0`.
These historical checks do not replace CI and installation checks on the
intended committed package revision.

Verification on one host does not establish results for the other supported
targets. The native release supports Linux x86_64, macOS arm64 and Windows x64;
the launcher must be exercised on each before claiming launcher support.

## Automated verification

The [Pub launcher workflow](../.github/workflows/pub-launcher.yml) checks
formatting, analysis and tests with Dart `3.13.0` and `3.13.5` on Linux, macOS
and Windows: six SDK/platform jobs. It does not download a native release or
publish the package. Results must be checked for the intended package revision;
the workflow definition alone does not establish a passing run.

The [fresh-install acceptance workflow](../.github/workflows/pub-acceptance.yml)
runs in `path` mode on changes to the launcher or acceptance harness. It checks
out the exact pushed SHA anonymously. Manual dispatch accepts a full immutable
`source_ref`, `mode` (`path` or `hosted`) and an exact launcher package `version`.
Use `path` before Pub upload and `hosted` after upload. The native version is
read separately from the launcher's pins, so a launcher patch need not change
the native CLI version.

Fresh acceptance uses Dart `3.13.5` on Linux, macOS and Windows, with isolated
`PUB_CACHE`, `DART_DATA_HOME` and `FAILFORGE_CACHE`. It installs the actual
command, runs setup and version checks, validates the manifested native payload,
and executes one real `RELATIONAL_BOUNDARY` mutant through direct and generated
YAML campaigns. It checks healthy original controls, one `KILLED` result per
campaign, matching IDs, preserved inputs and cleanup. HTML checks cover retained
Unicode/CRLF source, UTF-16 coordinates, embedded data, CSP and external resource
references. Hosted mode also compares the installed package payload with the
intended source revision.

The browser probe uses Playwright core `1.65.0` with a system Chrome/Edge browser
for offline desktop/mobile UI checks. A browser is required on Linux/Windows;
macOS records a skip if the required local browser tools are unavailable.
Screenshots stay on the runner and do not establish manual visual review.
The workflow grants no repository token permissions, performs no login or
publication, and prints synthetic verification receipts and bounded failure
logs without uploading artifacts.

The Python script's explicit local `--native-control` and `--fixture-only`
modes help validate the harness. They are forbidden in GitHub Actions, record
`launcherAcceptance: false`, and do not replace path or hosted installation
acceptance.

## Version and publication

Keep the Pub package version and native runtime version explicit. Launcher
`0.2.1` selects native `0.2.0`; the package and runtime have separate source
revisions and publication steps. The launcher must
select release-specific URLs and verified SHA-256 digests. Publishing the Dart
package does not bundle other native changes from the repository working tree.

For each package publication:

1. Identify the immutable package revision and the intended native release.
   Require the native release's exact-source CI, matching tag, three verified
   native archives and relocated fresh-cache smoke results.
2. Verify archive and manifest SHA-256 digests, then update launcher pins and
   package metadata in the committed package revision. Keep native and package
   source revisions distinct when the pin update follows the native build.
3. Require the six SDK/platform jobs and the three fresh `path` acceptance jobs
   for that package revision. Check Windows native installation and the console
   cancellation regressions alongside mutation/HTML smoke.
4. Review README/CHANGELOG, included files and `dart pub publish --dry-run`.
   SDKs, credentials, reports, caches and downloaded runtimes do not belong in
   the Pub payload. Run Pana on an isolated copy of the publishable files with
   the current stable Dart SDK, review every scoring category and record the
   tool versions. Pana can modify its input directory. Package CI enforces
   Dart core lints with `--fatal-infos`; the runnable example must also remain
   in the published archive. See the [Pub scoring guide](https://pub.dev/help/scoring).
5. Publish with the intended Google account. For an initial package, confirm
   that pub.dev accepts the intended name and records the intended uploader.
6. Dispatch fresh `hosted` acceptance against the same committed package
   revision after upload; check hosted installation, payload equality and real
   mutation/HTML results on all three platforms.

Publication is separate from verification. Local activation, `failforge setup`,
CI and `dart pub publish --dry-run` do not upload a Pub package.
See Dart's [publishing guide](https://dart.dev/tools/pub/publishing) for account
and package requirements.
