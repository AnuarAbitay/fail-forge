# Prepare the Pub launcher

`packages/failforge` is a local prototype of the Dart package that will expose
the `failforge` command through pub.dev. Launcher version `0.1.0-beta.1` installs
the existing native release `0.1.0`. Native release archives remain the source
of the Rust executables, Dart adapter and runtime notices.

Native `0.2.0` includes HTML export. The prototype's package version and `0.1.0`
runtime pins remain unchanged until the new native archives and their manifest
hashes have been verified. Launcher
`0.2.0` is the planned follow-up publication, not an already published package.

The adapter at `adapters/dart` remains an internal package with
`publish_to: none`. Publishing it alone would not provide the native CLI.

## Local checks

Use a stable Dart SDK `>=3.13.0 <4.0.0`:

```sh
cd packages/failforge
dart pub get
dart format --output=none --set-exit-if-changed .
dart analyze
dart test
dart pub publish --dry-run
```

The dry run validates and lists the package contents without uploading it.
Review that list before publication. The package should contain the launcher,
package metadata, README, CHANGELOG, LICENSE and NOTICE. Runtime downloads,
SDKs, local caches, reports and credentials do not belong in the Pub payload.

Check the `pubspec.yaml` content as part of that review:

- `name: failforge`, the intended package version and an accurate description.
- The supported Dart SDK range and only hosted or SDK dependencies.
- `executables` mapping the `failforge` command to `bin/failforge.dart`.
- Repository, issue tracker and supported platform metadata.
- No `publish_to: none` in the launcher package; retain it in the internal adapter.

From the repository root, exercise activation with a disposable Pub cache if
you need to keep the existing global installation unchanged:

```sh
export PUB_CACHE=/absolute/path/to/disposable-pub-cache
dart pub global activate --source path packages/failforge
"$PUB_CACHE/bin/failforge" setup
"$PUB_CACHE/bin/failforge" --version
```

On Windows, test the standard native CLI installer in a disposable install
directory as well as a disposable Pub cache:

```powershell
$env:PUB_CACHE = 'C:/absolute/path/to/disposable-pub-cache'
$env:DART_DATA_HOME = 'C:/absolute/path/to/disposable-dart-data'
$package = (Resolve-Path 'packages/failforge').Path.Replace('\', '/')
dart install "failforge@{path: '$package'}"
$launcher = Join-Path $env:DART_DATA_HOME 'install/bin/failforge.bat'
& $launcher setup
& $launcher --version
```

Run this example from the repository root. The batch command generated by
`dart install` starts the compiled native launcher. Legacy Pub global/VM
entry points are rejected on Windows before setup or a campaign starts because
the outer Dart VM broker cannot preserve Ctrl+Break cleanup and exit status.
When migrating an existing installation, first remove its stale command with
`dart pub global deactivate failforge`; manage the new installation with
`dart installed` and `dart uninstall failforge`.

Then use a prepared test package to run `doctor`, generate a profile and execute
a small mutation campaign. Check reports, source preservation and cleanup.
Also check Ctrl+C during a campaign, installation paths containing spaces,
repeated invocations, concurrent setup and recovery after interrupted setup.

### Local verification, 2026-11-10

On macOS arm64 with Dart 3.13.5:

- All 69 package tests passed, including argument/stdio preservation, Unix
  cancellation, independent SDK/Pub cache contexts and interprocess setup locks.
- Formatting and Dart analysis passed.
- `dart pub publish --dry-run` reported 0 warnings and a 17 KB compressed
  package. It did not upload anything.
- Local activation in a separate Pub cache downloaded the pinned native 0.1.0
  archive from GitHub over HTTPS and prepared its adapter at the final path.
- The installed command passed `--version`, `--help`, `doctor` and profile
  generation. A real Dart campaign produced one `KILLED` mutant, score 100%,
  exit code 0. Target inputs and the runtime's manifested payload stayed intact.
- All three native release archives extracted and passed manifest verification;
  execution through this launcher was checked on macOS arm64 only.

Local receipts and the saved mutation report are under the ignored directory
`artifacts/pub-launcher-20261110/`; `verification.json` records the commands and
source/payload checks. Local path activation may print dependency-resolution
messages from Pub before native stdout.

On Windows 11 Pro for Workstations x64 with Dart 3.13.5, launcher

- Activation through Pub's generated `failforge.bat`, fresh runtime download,

  workspaces were cleaned.
- Ten isolated console cases compared a delayed-cleanup fixture, the Dart
  wrapper, native CLI and the activated Pub batch command. Ctrl+C returned 130

The HTML feature added in native `0.2.0` was separately built and exercised
in real browsers
on Windows and Linux; see [HTML report verification](html-report.md#platform-verification).
Before a combined release, publish matching native archives containing that
feature and update the launcher's version-specific URLs and SHA-256 pins. This

checks do not replace CI on the intended committed release revision.

Verification on one host does not establish results for the other supported
targets. The native release supports Linux x86_64, macOS arm64 and Windows x64;
the launcher must be exercised on each before claiming launcher support.

The [Pub launcher workflow](../.github/workflows/pub-launcher.yml) is configured
to check formatting, analysis and tests with Dart `3.13.5` on Linux, macOS and
Windows when launcher files change. It does not download a native release or
publish the package. Adding the workflow does not establish that its jobs have
run or passed.

## Version and publication

Keep the Pub package version and native runtime version explicit. The launcher
must use release-specific archive URLs and matching SHA-256 digests. A new
native feature requires a new native release and a launcher update; publishing
this package does not ship the working tree's unreleased Rust changes.

Before the first publication:

1. Confirm the desired package name is available on pub.dev.
2. Finish the native `0.2.0` candidate in a clean committed revision. Require
   that exact revision's Linux/macOS and Windows CI, matching version tag,
   relocated fresh-cache package smoke and all three native archives.
3. Verify the native archive and manifest SHA-256 digests, then update the
   launcher's runtime version and pins in a separate follow-up commit. Archive
   hashes cannot be known before those exact native assets have been built;
   keep their native source revision distinct from the follow-up Pub revision.
4. Set the launcher package version to `0.2.0`, update README/CHANGELOG with
   verified release details, and repeat the local checks and fresh-cache
   install/mutation/HTML smoke on all three platforms. Use `dart install` on
   Windows and check real Ctrl+C/Ctrl+Break cleanup and exit codes.
5. Require the Pub launcher workflow's three platform jobs for that follow-up
   revision as well. The native uploader's existing CI gate does not check
   this separate workflow. Review `dart pub publish --dry-run` output.
6. Publish with the intended Google account, then check fresh hosted installs
   and real mutation/HTML runs on the supported platforms.

Initial publication is a separate step. No upload is performed by local
activation, `failforge setup` or `dart pub publish --dry-run`.

See Dart's [publishing guide](https://dart.dev/tools/pub/publishing) for account
and package requirements.
