Состояние на 2026-10-20. По просьбе пользователя проблемы сохранены для последующего решения; эта запись не означает, что они исправлены.

## Открытая подтверждённая проблема

### FF-001 — временная ошибка очистки при параллельном fork/exec

- **Статус:** причина воспроизведена, исправление не внесено.
- **Компонент:** `crates/failforge-profile/src/analysis/workspaces.rs`, `Workspace::close()`.
- **Симптом:** `workspace still has an active cleanup owner`. В параллельном Rust-наборе упал прежний тест `analysis::workspaces::tests::cleanup_unlinks_payload_alias_without_touching_target`.
- **Механизм:** посторонний дочерний процесс наследует дескриптор блокировки между `fork` и `exec`. Флаг `FD_CLOEXEC` закрывает его только при `exec`. Родитель уже закрыл свой дескриптор, но немедленная проверка через неблокирующий `flock` ещё видит блокировку у ребёнка.
- **Влияние:** очистка безопасно откладывается, однако возможна лишняя ошибка при одновременном создании процессов, в том числе при параллельных вызовах API профилей. Это не исключительно проблема тестового набора.
- **Доказательство:** отдельный Rust-сценарий с неизменённым модулем из `de09daeb` воспроизвёл точную ошибку **3 из 3 раз**. После разрешения `exec` очистка проходила, хотя посторонний процесс продолжал работать. Контроль без параллельного `fork` проходил; цели символических ссылок не изменялись.
- **Граница доказательства:** PID владельца блокировки в первоначальном падении не записан. Связь именно того падения с соседним тестом discovery остаётся предположением; сам механизм и совпадающая ошибка подтверждены.
- **При исправлении:** сохранить запрет удаления окружения с действительным владельцем; проверить окно fork/exec, действительно активного владельца, ограниченность ожидания, отмену, подмену каталогов и параллельные вызовы. Последовательный зелёный прогон сам по себе исправлением не считается.

## Наблюдение, требующее отдельного разбора

### FF-002 — ошибка повторного сигнала при завершившемся процессе на macOS

- **Статус:** сохранён конкретный результат Runner; причина системного `EPERM` ещё не доказана, исправление не внесено.
- **Сценарий:** адаптер ответил на handshake, но задержал завершение после EOF. По истечении срока закрытия владелец запросил существующий путь принудительной отмены.
- **Наблюдение:** SIGTERM отправлен успешно; следующий SIGKILL вернул `errno: 1`. Процесс завершился от SIGTERM, `child_reaped: true`, группа — `NoLiveMembers { zombies: 1 }`, оба потока полностью захвачены. Из-за ошибки сигнала `cleanup.is_complete()` остался `false`.
- **Граница вывода:** порядок событий согласуется с гонкой завершения и повторного сигнала, но не доказывает точную причину `EPERM`. Не измерена частота воспроизведения. Наличие живого или незабранного дочернего процесса этим результатом не подтверждается.
- **Текущее поведение:** discovery сохраняет реальный receipt и возвращает инфраструктурную ошибку; неполная очистка не переименовывается в успешную отмену.
- **Доказательство:** `artifacts/discovery-migration/2026-10-19/validation/close-deadline-observation.md`.

## Оставшиеся этапы переноса на Rust

Это незавершённые работы по архитектуре, а не подтверждённые ошибки поведения:

1. Публикация результатов: manifests, журнал событий, текущие progress/checkpoints и атомарная запись итоговых файлов. Итоговые summary, score и таблицу терминала уже формирует Rust. Python пока также передаёт нормализованную конфигурацию, окружение и сигналы нативному владельцу.
2. Перенос или удаление оставшихся диагностических, установочных, измерительных и регрессионных Python-инструментов; удаление временных прослоек совместимости после проверки замен.

Полный цикл **одной попытки** уже перенесён в Rust: выделение свежей копии, копирование, namespace isolation, применение проверенного патча, запуск Runner, проверка захваченного вывода и исходников, очистка и публикация результата. Python пока сохраняет агрегированные отчёты кампании.

Этап **discovery** также перенесён: нативный владелец запускает `AdapterClient` напрямую, проверяет протокол и кандидатов, аутентифицирует захваченный вывод, проверяет неизменность исходников и пишет журнал и receipt. Python передаёт один приватный запрос и проверяет форму ответа. Старый helper пока нужен генерации профилей и диагностическим инструментам.

Полный цикл **одного мутанта** перенесён в Rust: повторная проверка кандидата и патча, статический `INVALID` без запуска SDK, начальная попытка, до трёх причинных контролей, проверка привязки входных данных между контролями и публикация итоговой записи. Все попытки выполняются напрямую через общий Rust-код со свежими копиями; Python больше не планирует причинные контроли и не переписывает итоговую запись на production-пути. Начальное наблюдение сохраняется отдельно в `attempt.json`, окончательный результат — в `result.json`.

Выполнение **одного семейства** также перенесено: один Rust-владелец запускает baseline, ограниченную очередь мутантов и заключительный контроль оригинала. Он напрямую вызывает общий код попыток и мутантов, удерживает приватные данные baseline и namespace, проверяет входные данные до и после семейства, ожидает все начатые задачи при отмене. Результаты передаются последовательно нумерованными JSONL-событиями с итоговым SHA-256 всего предшествующего потока. Python сохраняет агрегированные отчёты и прогресс, включая поздние результаты уже начатых задач. Пустой прямой запуск сохраняет оба контроля оригинала; пустое семейство профиля не запускает авторские тесты.

**Планирование всей кампании на готовом snapshot** также выполняет Rust. Сначала выполняются все discovery и проверка общего лимита, затем семейства последовательно запускаются в порядке `classic → failure_mode → language_specific`. Общие реализации discovery, семейства, мутанта и попытки вызываются внутри процесса. Ошибка или отмена останавливает дальнейший запуск; уже начатые владельцы завершаются с очисткой. Проверки оригинала и привязки входных данных выполняются также после ошибки или отмены. Отдельный `campaign-execute` остаётся диагностическим интерфейсом.

**Подготовка и завершение всей кампании** теперь принадлежат одному Rust-процессу `campaign-run`. Оба публичных режима передают ему нормализованные настройки. Он выполняет preflight до создания отчёта, проверяет инструменты и расположение каталогов, создаёт output, восстанавливает registry, выделяет snapshot, копирует и связывает входные данные, вызывает общий планировщик, очищает рабочие копии и повторно проверяет оригинал. Финальные проверки и очистка выполняются независимо от отмены. Python больше не вызывает отдельные workspace-inputs/workspace-lifecycle операции на публичном пути и не удерживает дескрипторы рабочих копий. Отчёты создаются после события `prepared`; успех требует подтверждённой cleanup-квитанции и SHA-256 всего потока событий.

**Итоговый отчёт** вычисляет Rust: после завершения владельца и последних обработчиков событий один чистый `campaign-report` формирует сводку, счётчики, отдельные score семейств и таблицу терминала. Для расчёта передаются только идентификаторы, исходы, причины и метаданные; подробные доказательства попыток прикрепляются обратно без изменений. Это сохраняет большие записи без повторной передачи через ограниченный служебный канал. Ошибка записи приводит к пересчёту неполного отчёта и таблицы; ошибка самого Rust-формирователя не включает Python fallback. Атомарный publisher профиля пока остаётся прежним.

## Уже исправлено в текущем рабочем дереве

Не возвращать в список открытых проблем без нового воспроизведения:

- Подмена символической ссылки в пути к каталогу отчёта: добавлены проверки привязки пути и канонический путь для файлов захвата и planner.
- Сохранение приватных данных для повторного использования после инфраструктурной ошибки или отмены: данные отзываются, повторная подготовка namespace сериализуется, артефакты плана размещаются внутри отдельной попытки.
- При переносе полного цикла мутанта финальная перепроверка исходника скрывала уже записанный `INFRA_ERROR/source_input_changed`, возвращая 125 без итоговой записи. Процессный тест подтвердил регресс; исправление сохраняет аутентифицированную диагностику и отзывает подтверждение убийства. Отдельный тест проверяет приоритет ошибки исходника над отменой при отсутствии готового результата.
- При переносе семейства отмена из обработчика прогресса или `native_completed` могла скрыть ошибку нативного выполнения либо отсутствие завершающего события. Регрессионные тесты подтвердили ошибку; теперь статус процесса и проверенное завершающее событие имеют приоритет над такой отменой.
- Произвольная ошибка обработчика прогресса, например `RuntimeError`, выходила за границу обработки ошибок прямой кампании. Теперь она сохраняется в итоговом отчёте со статусом `failed`, как и в запуске через профиль. Тесты обоих вариантов подтверждают сохранение поздних результатов, отсутствие score и очистку snapshot.
- При переносе планировщика ошибка `verify_inputs` после успешно завершённого семейства теряла привязку к этому семейству в агрегированном отчёте. Регрессионный тест падал до исправления и проходит после него: профиль и затронутое семейство получают `failed`, score не публикуется.
- Ошибка ограничения размера discovery-события могла оставить открытый этап в потоке планировщика. Проверка размера теперь входит в завершаемую фазу; тест граничного размера подтверждает сбалансированное завершение, сохранение префикса и подлинный итог `failed`.
- При переносе жизненного цикла общая очистка удаляла подменённый каталог snapshot после того, как проверка сохранённого inode уже отказала в его удалении. Регрессионный тест воспроизвёл удаление контрольного файла. Теперь отказ точечной очистки блокирует общий reaper: через сохранённый дескриптор кампании создаётся `.cleanup-blocked`, возвращаются `cleanupDeferred: true` и `snapshotCleaned: false`. Следующий recovery тоже сохраняет этот каталог для разбора. Тесты подтверждают сохранение заменившего каталога, перемещённого snapshot, чужого registry и существующего маркера.
- На новом переходе preflight → controller классические операторы по умолчанию раскрывались в список, хотя прежний контракт оставлял поле отсутствующим. Контракт сохранён; отдельные Rust-, bridge- и процессный тесты проверяют `classic` без явного списка операторов.

Эти ошибки подтверждены тестами, исправлены и перепроверены.
